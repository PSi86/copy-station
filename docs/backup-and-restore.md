# Backing up and restoring a station

How to save everything that makes *your* station yours, and put it back on a
freshly imaged card. Applies to both supported boards (Radxa Cubie A7S,
Raspberry Pi 4/5).

The short version: **two files and one OS setting.** Everything else is either
generated by `scripts/install.sh` or recreated by the daemon at runtime.

---

## 1. What to back up

| # | What | Where | Why |
|---|---|---|---|
| 1 | Your configuration | `/etc/copystation/config.yaml` | GPIO pins, display model, transcode presets, AP password — everything you set up |
| 2 | The runtime settings overlay | `/var/lib/copystation/user-settings.json` | Toggles made from the web UI or a user button. **It wins over `config.yaml`** |
| 3 | The SPI overlay | an OS setting, not a file | Enables `/dev/spidev*`, without which an e-paper or WS2812 backend cannot start |

### Why the overlay file matters more than it looks

`user-settings.json` holds the settings that are changed at *runtime* and must
survive a restart without rewriting the (commented) config: auto-transcode
on/off, the default transcode preset, the transcode output location, and the
WiFi AP on/off state.

When it is present it **overrides** the corresponding values in `config.yaml`.
So a station whose config says `wifi_ap.enabled: false` can perfectly well come
up with the AP running, because someone switched it on once and the overlay
remembered. Restore only the config and that station comes back subtly
different from the one you backed up — the AP down, the preset reset.

If you would rather start clean, just delete the file: the config values then
apply again.

### Nice to have

- `/var/lib/copystation/transcode-perf.json` — measured throughput per
  source/preset combination, which is what the web UI's job-time estimates are
  built from. It re-learns itself after a few jobs, so this only saves you the
  first few inaccurate estimates.

## 2. What you do *not* need to back up

Worth knowing, so a restore does not turn into a hunt for state that was never
there:

| | Why not |
|---|---|
| The WiFi AP's NetworkManager profile | The daemon **deletes and re-creates it from `config.yaml`** every time the AP is raised, so the profile can never drift from the config. Backing it up would be backing up a cache. |
| `/opt/copystation` (code + venv) | Entirely produced by `scripts/install.sh`. |
| `/etc/systemd/system/copystation.service` | Installed from `systemd/copystation.service` in the repo. |
| The repo checkout | Clone it again. Keep your own commits on a branch you pushed, of course. |
| `/run/copystation/**` | Mountpoints and scratch space on tmpfs — gone at every boot by design. |
| udev rules | There are none. Device detection is `pyudev` inside the daemon. |
| Package lists | `scripts/install.sh` installs every dependency the project needs. |

## 3. Taking the backup

From another machine, over SSH. Nothing here needs root on the station: the
config and the state files are world-readable.

```bash
STATION=user@station-ip                      # e.g. radxa@192.168.2.111
BK=~/copystation-backup/$(date +%F)
mkdir -p "$BK"/{etc,var,inventory}

# 1. your configuration -- this one must succeed
scp "$STATION":/etc/copystation/config.yaml "$BK/etc/"

# 2. the runtime overlay. Absent on a station where nothing was ever toggled
#    from the web UI or a button -- that is normal, not an error.
scp "$STATION":/var/lib/copystation/user-settings.json "$BK/var/" \
  || echo "no overlay on this station; the config values apply as-is"

# 3. nice to have -- the learned job-time estimates
scp "$STATION":/var/lib/copystation/transcode-perf.json "$BK/var/" \
  || echo "no measurements yet"
```

### Record the state you are restoring *to*

Not required, but it is what turns "the restore ran" into "the restore is
correct", and it is the only way to notice a GPIO offset that moved:

```bash
ssh "$STATION" '
  tr -d "\0" < /proc/device-tree/model; echo; uname -r
  grep __version__ /opt/copystation/copystation/__init__.py
  systemctl is-enabled copystation; systemctl is-active copystation
  ls -l /dev/spidev* 2>/dev/null || echo "no SPI node"
  gpiodetect
' > "$BK/inventory/system-state.txt"

# GPIO offsets WITH their header-pin names -- see the warning in section 5
ssh "$STATION" gpioinfo > "$BK/inventory/gpio-lines.txt"
```

> **Your config may contain secrets** — `wifi_ap.password` and, if you enabled
> it, `web.auth.password`. Keep the backup out of any repository you push.

## 4. Restoring onto a fresh image

### Step 1 — install the OS and enable SPI *(manual)*

Flash the board's image, create your login user, get it on the network.

Then enable SPI, **if** your config uses an `epaper` or `ws2812` backend —
without it there is no `/dev/spidev*` node and the display cannot start:

- **Raspberry Pi** — `sudo raspi-config` → Interface Options → SPI (or
  `dtparam=spi=on` in `/boot/firmware/config.txt`). Gives `/dev/spidev0.0`.
- **Radxa Cubie A7S** — `sudo rsetup` → Overlays → enable `spidev on SPI1`.
  Gives `/dev/spidev1.0`.

Reboot, then confirm with `ls /dev/spidev*`. On the Cubie A7S, a warm `reboot`
works from kernel `6.6.98-4-aw2511` onwards but **never came back on the older
`6.6.98-3`** — check `uname -r`, and power-cycle instead if you are on an older or
unknown image (see the README's "Powering off safely").

### Step 2 — install, with your config

```bash
sudo apt-get update && sudo apt-get install -y git
git clone https://github.com/PSi86/copy-station.git ~/copy-station

# Passing the config as an argument installs it VERBATIM -- the installer only
# offers its interactive tweaks when it falls back to a bundled example.
sudo bash ~/copy-station/scripts/install.sh /path/to/backup/etc/config.yaml
```

### Step 3 — put the runtime overlay back

The step that is easy to forget, and the one that makes the station behave the
way it did before rather than the way its config file reads:

```bash
sudo install -d /var/lib/copystation
sudo install -m 644 /path/to/backup/var/user-settings.json \
                    /var/lib/copystation/user-settings.json
# optional: the learned job-time estimates
sudo install -m 644 /path/to/backup/var/transcode-perf.json \
                    /var/lib/copystation/transcode-perf.json
sudo systemctl restart copystation
```

Skip this to deliberately start from the config's own values.

### Step 4 — verify

```bash
systemctl status copystation
journalctl -u copystation -b -p warning     # GPIO conflicts show up here
ls -l /dev/spidev*                          # if you use a SPI backend
curl -sI http://localhost:8080/ | head -1   # if the web interface is on
```

A `GPIO line conflict` or a `Device or resource busy` (EBUSY) in the log means
two enabled features want the same line — see the pin notes in the README.

Then the parts only hardware can confirm: the display draws a frame the right
way up, the user button's gestures do what they should, the access point comes
up if it is meant to, and one real copy (plus a transcode, if enabled) runs
through.

## 5. If GPIO stops working after a new image

**Line offsets are kernel- and device-tree-dependent. Header pin numbers are
not.** A kernel update can renumber the lines under you, and the symptom is a
config that used to be right suddenly driving the wrong pin — or failing to
claim one at all.

This is why section 3 saves `gpioinfo` output: it names each line by its
physical pin, so you can re-derive the offsets rather than guess them.

```bash
gpioinfo | grep -E 'PIN_(10|16|18|22)\b'    # the pins your hardware sits on
```

Read the offset from the `line N:` column and put that into `config.yaml`. On a
Raspberry Pi the offset equals the BCM number, so this rarely bites; on the
Cubie A7S the offset is `(bank_letter - 'A') * 32 + pin_number` (PB10 = 42,
PJ24 = 312), and a board can expose more than one `gpiochip` — confirm with
`gpiodetect` and set `gpiochip:` accordingly.

## 6. Moving a config between versions

A config from an older release keeps working: keys added since simply fall back
to their defaults. So a verbatim restore is always the safe option.

A key that has been *retired* is ignored silently, with one exception — the old
`power.shutdown_button` is called out at startup ("no longer supported — migrate
to `buttons.userbutton_1`"), and `scripts/install.sh` refuses to let it pass
unmentioned. So do not read a quiet log as proof that every key still applies;
compare the effective settings if it matters.

To move onto the current, fully-commented example instead, diff the two by
their *effective* settings rather than by text — that way defaults filled in for
absent keys are compared too, and you see behavioural differences instead of
comment churn:

```python
from copystation.config import load_config

a, b = load_config("old-config.yaml"), load_config("new-config.yaml")
# compare a.data and b.data
```
